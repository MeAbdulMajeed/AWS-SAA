## 1. Scalability vs. High Availability

| Term | Meaning | EC2 example |
|---|---|---|
| **Vertical scaling** (scale up/down) | Bigger or smaller instance | t2.micro → t2.large |
| **Horizontal scaling** (scale out/in) | More or fewer instances; implies a distributed system. Also called **elasticity**. | Add instances to an ASG |
| **High availability** | Run the same app in **at least 2 AZs** to survive a data center loss | ASG or load balancer with multi-AZ enabled |

- **Vertical** suits non-distributed systems like databases (RDS, ElastiCache scale by changing instance type), but has a hardware ceiling.
- **Horizontal** is the standard for web and modern apps.
- HA often goes hand in hand with horizontal scaling, **but not always**. HA can be **passive** (RDS Multi-AZ: a standby waits) or **active** (several instances in several AZs all serving traffic).
- Exam trap: scalability and HA are linked but different. "Survive an AZ failure" = HA (multi-AZ). "Handle more load" = scalability.
- ⚠️ The lecture quotes the smallest instance (t2.nano) and the biggest (u-12tb1.metal, 12.3 TB RAM). AWS has released larger instances since. Don't memorize the extremes.

## 2. Elastic Load Balancing (ELB) — Overview

A load balancer forwards incoming traffic to multiple backend (downstream) targets. Users see **one endpoint** and never know which instance served them.

**Why use one:**
- Single point of access (a fixed DNS name)
- Seamlessly handles failed downstream instances (via **health checks**)
- SSL/TLS termination, stickiness with cookies, HA across AZs
- Separates public traffic from private traffic
- **Managed by AWS:** upgrades, maintenance and HA are handled for you. Cheaper than running your own.
- Integrates with EC2, ASG, ECS, ACM, CloudWatch, Route 53, WAF, Global Accelerator.

### Health checks
- Done at the **target group** level using a protocol, port and path (e.g. HTTP, port 4567, `/health`).
- A target returning **HTTP 200** is healthy. Anything else marks it **unhealthy**, and the LB stops sending it traffic.
- ➕ The "healthy" response codes are configurable (default 200 for ALB).

### The 4 load balancer types
| Type | Launched | Layer | Protocols |
|---|---|---|---|
| **Classic (CLB)** | 2009, "v1" | 4 and 7 | HTTP, HTTPS, TCP, SSL |
| **Application (ALB)** | 2016 | **7** | HTTP, HTTPS, WebSocket |
| **Network (NLB)** | 2017 | **4** | TCP, TLS, UDP |
| **Gateway (GWLB)** | 2020 | **3** | IP packets |

- ⚠️ **CLB:** the course says it is deprecated and the exam no longer references it. AWS calls it "previous generation" and recommends ALB/NLB. ✔ What was retired is **EC2-Classic networking**, not the CLB itself, and I could not confirm a CLB shutdown date. Treat "CLB is going away soon" as unconfirmed. Practical rule: if a CLB shows up as an answer, it is almost always the wrong one.
- Load balancers can be **internal** (private) or **internet-facing** (public).

### Security group pattern (very common exam scenario)
- **LB security group:** inbound **80/443** from `0.0.0.0/0`.
- **EC2 security group:** inbound 80 with the **source set to the LB's security group** (not an IP range).
- Effect: instances only accept traffic that originates from the load balancer.
- **Verified in the hands-on:** after this change, hitting an instance's public IP directly **times out**, while the LB DNS name still works. (Timeout = security group issue, same rule as before.)

## 3. Application Load Balancer (ALB) — Layer 7

- Routes **HTTP/HTTPS/WebSocket**, supports **HTTP/2**, and can **redirect** (e.g. HTTP → HTTPS) at the LB.
- **One ALB can front many applications** (with CLB you needed one LB per app).
- Great for **microservices and containers**: ALB has **dynamic port mapping** for ECS.
- Gets a **fixed DNS hostname** (not a fixed IP).

### Target groups
Targets can be:
1. **EC2 instances** (often managed by an ASG)
2. **ECS tasks**
3. **Lambda functions**
4. **IP addresses** (must be **private** IPs; can include on-premises servers reachable over VPN/Direct Connect)

Health checks happen **per target group**.

### Listener rules
- Conditions: **path** (`/users`, `/search`), **host** (`one.example.com`), **HTTP header**, **HTTP method**, **query string** (`?Platform=Mobile`), **source IP**.
- Actions: **forward** to target group(s), **redirect**, or return a **fixed response** (e.g. 404 + custom text).
- **Priority** decides which rule wins when several match (1 is the highest priority, up to 50,000).
- Hands-on: a rule "path = `/error` → fixed response 404" returned the custom error only when `/error` was requested. Everything else hit the default rule.

### Client IP visibility
- ALB **terminates the connection** and opens a new one to the target, so the app sees the **ALB's private IP**.
- Real client info arrives in headers: **`X-Forwarded-For`** (client IP), **`X-Forwarded-Port`**, **`X-Forwarded-Proto`**.

### ➕ SAA extras on ALB
- Attach **AWS WAF** to an ALB (WAF cannot attach to an NLB).
- Can authenticate users via **Cognito or OIDC** at the listener.
- ALB **cannot have an Elastic IP / static IP**. For static IPs: put an **NLB in front** (see below) or use **Global Accelerator**.
- ✔ **Slow start** (30–900 s, off by default) lets a new target ramp up traffic gradually. Default routing algorithm is round robin; **least outstanding requests** is an option.

## 4. Network Load Balancer (NLB) — Layer 4

- Handles **TCP, TLS, UDP**. Exam rule: **"UDP" or "TCP at extreme scale" → NLB**.
- **Millions of requests/second, ultra-low latency.**
- **One static IP per AZ**, and you can attach an **Elastic IP** to each. Exam rule: **"application can only be reached via 1–3 fixed IPs" → NLB**.
- **Not free tier.** Delete after labs.
- Targets: **EC2 instances**, **private IP addresses** (including on-prem servers), or an **ALB**.
  - **NLB in front of ALB** is valid: you get **fixed IPs from the NLB** and **HTTP routing rules from the ALB**.
- Health checks support **TCP, HTTP, HTTPS**.
- ⚠️ The lecture notes that NLBs can now have a **security group** attached (newer than the older "NLB has no SG" behavior). Hands-on gotcha: the instances showed **unhealthy** until their security group was changed to allow traffic from the **NLB's security group** (the earlier rule only allowed the ALB's SG). Lesson: every LB in front of an instance needs to be allowed in the instance's SG.

### ➕ SAA extras on NLB
- **AWS PrivateLink** (exposing your service to other VPCs) requires an **NLB** (or GWLB).
- NLB can **preserve the client's source IP** to the targets.

## 5. Gateway Load Balancer (GWLB) — Layer 3

- Purpose: **deploy, scale and manage a fleet of third-party virtual network appliances**: firewalls, intrusion detection/prevention (IDS/IPS), deep packet inspection, payload modification.
- Two functions in one:
  1. **Transparent network gateway:** a single entry and exit for all VPC traffic.
  2. **Load balancer:** spreads that traffic across the appliances.
- Flow: user traffic → GWLB → appliances (inspect / drop) → back to GWLB → application. Transparent to the app. Route tables are modified to make this happen.
- Uses the **GENEVE protocol on port 6081**. If an exam question says GENEVE or 6081, the answer is **GWLB**.
- Targets: **EC2 instances (by instance ID)** or **private IP addresses** (e.g. appliances in your own data center).
- The lecture skips the hands-on. Know the diagram, not the setup.

## 6. Sticky Sessions (Session Affinity)

- The same client keeps being sent to the **same backend instance**.
- The lecture says it works with **CLB, ALB, NLB**. ⚠️ ✔ Detail: ALB stickiness is **cookie-based**; NLB stickiness is based on **source IP**, not cookies.
- Use case: don't lose **session data** (e.g. login state) held on one instance.
- Downside: can create **imbalanced load** if some instances have very "sticky" users.

### Cookie types (ALB)
| Type | Generated by | Cookie name | Duration |
|---|---|---|---|
| **Duration-based** | Load balancer | `AWSALB` (ALB), `AWSELB` (CLB) | Set by the LB (1 second to 7 days) |
| **Application-based, LB-generated** | Load balancer | `AWSALBAPP` | Set by the application |
| **Application-based, custom** | Your application | Your own name | Set by your application |

- ⚠️ Reserved names you must **not** use for a custom cookie: `AWSALB`, `AWSALBAPP`, `AWSALBTG` (the transcript text garbled these).
- You don't need to memorize every name, just that app-based and duration-based exist.
- Setting: **target group → Attributes → Stickiness**. ✔ Default duration is 1 day.
- **Verified in the hands-on:** with stickiness on, refreshing kept hitting the **same instance**; the browser devtools showed the cookie being set and then sent back.

### ➕ Exam pattern
Stickiness keeps users on one instance, but if that instance is **terminated** (scale-in, failure), the session is lost anyway. The robust fix is to **store session data externally** (**ElastiCache** or **DynamoDB**) so any instance can serve any user.

## 7. Cross-Zone Load Balancing

Each LB node distributes traffic either to **all targets in all AZs** (cross-zone on) or **only to targets in its own AZ** (off).

Example: 2 instances in AZ-a, 8 in AZ-b.
- **Cross-zone ON:** every instance gets **10%**.
- **Cross-zone OFF:** AZ-a instances get **25% each**, AZ-b instances get **6.25% each** (imbalanced).

| LB | Default | Inter-AZ data charges |
|---|---|---|
| **ALB** | **ON** (always on at LB level; can be overridden **per target group**) | **No charge** |
| **NLB** | **OFF** | **Charged** if enabled |
| **GWLB** | **OFF** | **Charged** if enabled |
| CLB | OFF | No charge if enabled |

## 8. SSL/TLS Certificates on Load Balancers

- An SSL/TLS certificate encrypts traffic **in flight** between clients and the LB. TLS is the newer standard, but everyone still says "SSL".
- Public certs are issued by Certificate Authorities (Digicert, GlobalSign, Let's Encrypt, etc.) and **expire**, so they must be renewed.
- Flow: clients connect over **HTTPS** → LB does **SSL termination** → LB talks to EC2 over **plain HTTP** inside the VPC (private network).
- LB uses an **X.509 certificate**, typically managed in **AWS Certificate Manager (ACM)**. You can also **import** your own certificate into ACM.
- An **HTTPS listener** must have a **default certificate**; you can add more.
- You can set a **security policy** (e.g. to support legacy SSL/TLS clients).
- ⚠️ The hands-on transcript says "port 403 for HTTPS". That's a typo. HTTPS is **443**. (Also, IAM as a certificate source is **not recommended**; use ACM.)
- ➕ **Imported vs. ACM-issued:** ACM-issued public certs **auto-renew**. **Imported certificates (e.g. from an external CA) do NOT auto-renew**, so you must rotate them yourself (typically alerted via EventBridge before expiry). This distinction appeared in your institute assessment.

### SNI (Server Name Indication)
- Solves: **serving multiple HTTPS websites, each with its own certificate, from one load balancer.**
- The client states the **hostname** it wants during the TLS handshake, and the LB picks the matching certificate.
- Supported on **ALB, NLB, CloudFront**. **NOT supported on CLB** (CLB = one certificate only).
- Exam rule: **"multiple SSL certificates on one load balancer" → ALB or NLB (SNI).**

## 9. Connection Draining / Deregistration Delay

- Gives an instance time to finish **in-flight requests** while it's being **deregistered or marked unhealthy**. New requests go only to other instances.
- Name: **Connection Draining** on CLB, **Deregistration Delay** on ALB/NLB.
- ✔ Range **0–3600 seconds**, **default 300 seconds (5 minutes)** on ALB/NLB. **0 disables it** (the lecture quotes 1–3600 for the CLB).
- Short requests → low value (instance leaves faster). Long requests or uploads → high value (trade-off: instance lingers longer).
- ➕ An ASG respects this when scaling in, so long uploads don't get cut off if the delay is long enough.

## 10. Auto Scaling Groups (ASG)

**Goal:** scale **out** (add instances) when load rises and scale **in** (remove instances) when it falls, within limits.

- **Capacity settings:** **minimum**, **desired**, **maximum**. The group never goes outside min/max.
- **Free:** the ASG itself costs nothing. You pay for the resources it creates (EC2 etc.).
- **Self-healing:** an instance deemed unhealthy is **terminated and replaced**.
- **With a load balancer:** instances are registered to the LB's target group automatically, and new instances start receiving traffic.
- **Health checks:** **EC2 status checks** and optionally **ELB health checks**. When ELB health checks are enabled, the ASG **terminates instances the load balancer marks unhealthy**.
  - ➕ Exam trap: by default an ASG only checks that the instance is running. An instance can pass EC2 checks while the **app is broken**. Enable the **ELB health check type** so the ASG replaces it.
- **Multi-AZ:** pick several AZs/subnets. "Balanced best effort" distribution spreads instances across AZs.

### Launch template
Defines **how** the ASG launches instances: AMI, instance type, user data, EBS volumes, security groups, key pair, IAM role, network/subnet info, LB info.
- ⚠️ ✔ **Launch configurations are deprecated.** Accounts created on or after **Oct 1, 2024** can't create new ones at all, and newer instance types aren't supported. Always use **launch templates** (versioned, support mixed Spot/On-Demand, newer features).

### Hands-on lessons
- Created 1 instance via the ASG (min = desired = max = 1). Activity history showed "launching a new instance".
- The new instance showed **unhealthy** in the target group while it was still bootstrapping, then became healthy.
- Changing desired capacity 1 → 2 launched another instance. Setting it back to 1 **terminated** one (and deregistered it).
- If an instance **never gets healthy**, the ASG keeps **terminating and relaunching** it. Usual causes: a **security group** problem or a broken **user data** script.

### ➕ SAA extras on ASG (from general AWS knowledge; not re-checked in tonight's lookups)
- **Default termination policy (scale-in):** picks the AZ with the most instances first, then (within it) the instance using the oldest launch template/configuration, then a tiebreaker. This keeps AZs balanced.
- **Health check grace period:** time the ASG waits after launch before checking health (300 s in the console). Set it longer than your app's boot time to avoid launch/terminate loops.
- **Lifecycle hooks:** pause an instance in **Pending** or **Terminating** state to run custom actions (install software, drain logs).
- **Warm pools:** pre-initialized instances to speed up scale-out.
- **Instance refresh:** roll out a new AMI/launch template gradually.
- **Scale-in protection:** stop specific instances being terminated by scale-in.
- **Mixed instances policy:** combine On-Demand and Spot, multiple instance types.

## 11. ASG Scaling Policies

| Policy | How it works | Use when |
|---|---|---|
| **Target tracking** | Pick a metric and a target value (e.g. avg CPU = 40%). The ASG adds/removes instances to hold it there. | Simplest. Recommended default. |
| **Simple scaling** | One CloudWatch alarm → add/remove a fixed amount (e.g. +2 or +10%). | Basic, older style. |
| **Step scaling** | CloudWatch alarm with **tiered steps** (very high → add 10, a bit high → add 1). | Different reactions to different severity. |
| **Scheduled** | Change min/desired/max at a **specific time**. | A **known** event (promotion next Saturday, 5 PM Fridays). |
| **Predictive** | **ML forecast** from historical load, scales **ahead of time**. | **Cyclical/repeating** patterns. |

- Policies fall into **dynamic scaling** (target tracking, simple, step), **scheduled**, and **predictive**.
- **Target tracking** automatically **creates two CloudWatch alarms**: AlarmHigh (scale out) and AlarmLow (scale in).
- **Hands-on results:**
  - Target tracking, CPU target 40%. Ran `stress` to push CPU to ~100%, and the ASG scaled **1 → 2 → 3** instances.
  - After stopping the load, it **scaled back in** (3 → 2 → 1).
  - **Scale-in is deliberately slower than scale-out.** In the demo, the high alarm needed 3 datapoints within 3 minutes, while the low alarm needed **15 datapoints (about 15 minutes)**.
  - ⚠️ The transcript is garbled about the exact low-alarm threshold ("28%"). Exact numbers are not exam material.
  - ⚠️ The demo command is `stress -c 4` (lowercase `c`), not `-C`.
  - Reminder: delete the policy during cleanup.

### Good metrics to scale on
- **Average CPU utilization** (the default choice).
- **RequestCountPerTarget** (from the ALB): average requests per instance.
- **Average network in/out**, for network-bound apps (lots of uploads/downloads).
- **Any custom CloudWatch metric** you publish.

### Predictive scaling details ✔
- Needs **at least 24 hours** of historical data before it forecasts.
- Produces an **hourly forecast for the next 48 hours**, refreshed **every 6 hours**.
- Starts in **forecast only** mode so you can review, then switch to **forecast and scale**.
- Best for cyclical patterns. It is not for a one-off event (use scheduled).

### Cooldown vs. warmup (the lecture simplifies this) ✔
- **Scaling cooldown:** after a scale activity, wait **300 seconds (5 min) by default** before another, so metrics can stabilize.
- ✔ **Nuance:** the default cooldown applies to **simple scaling** policies. **Target tracking and step scaling** don't wait for a cooldown; they use an **instance warmup** period instead (a new instance isn't counted in the metrics until it is warm).
- Tips from the lecture: use a **pre-baked (ready-to-use) AMI** so instances serve traffic faster, which lets you shorten the cooldown. Enable **detailed monitoring** (1-minute metrics) for faster reaction.

## Exam cheat sheet: "If you see X, think Y"
| You see... | Think... |
|---|---|
| HTTP/HTTPS, path/host/query-based routing, microservices, Lambda or containers as targets | **ALB** |
| UDP, extreme performance, millions of req/s | **NLB** |
| App must be reachable via 1–3 **fixed/static IPs** | **NLB (Elastic IP per AZ)**, or Global Accelerator; ALB can't |
| Fixed IPs **and** HTTP path routing | **NLB in front of ALB** |
| Firewall / IDS / third-party virtual appliances, GENEVE, port 6081 | **GWLB** |
| Multiple SSL certificates on one LB | **ALB / NLB with SNI** (not CLB) |
| Keep a user on the same instance | **Sticky sessions**; but externalize sessions (ElastiCache/DynamoDB) for resilience |
| Uneven traffic across AZs with different instance counts | **Cross-zone load balancing** (NLB/GWLB: charges apply) |
| In-flight requests cut off during scale-in | Increase **deregistration delay** |
| Instance passes EC2 checks but app is broken | Enable **ELB health checks** on the ASG |
| Keep CPU near a number, least effort | **Target tracking** |
| Known event at a known time | **Scheduled scaling** |
| Repeating daily/weekly pattern, need capacity *before* it hits | **Predictive scaling** |
| EC2 only reachable through the LB | EC2 SG allows the **LB's security group** as source |
| Old "launch configuration" | Migrate to **launch template** |

## Quick recap
- **HA** = multi-AZ. **Scalability** = vertical (bigger) or horizontal (more).
- **ALB** (L7, smart routing), **NLB** (L4, speed, static IPs, UDP), **GWLB** (L3, security appliances), **CLB** (previous generation, avoid).
- Health checks decide who gets traffic. Cross-zone defaults: ALB on, NLB/GWLB off.
- SNI = multiple certificates on one LB (ALB/NLB, not CLB).
- **ASG** = min/desired/max, self-healing, multi-AZ, integrates with ELB health checks, launched from a **launch template**.
- **Scaling:** target tracking (simplest), step/simple (alarms), scheduled (known), predictive (cyclical, ML).
